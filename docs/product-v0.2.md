## 1. 产品主张与范围

Mc4Need 帮助发起方提出明确的餐食需求，让赞助人通过自己的麦当劳账号承担整单，并看到收餐反馈与致谢。支持单次需求和逐期确认的重复需求。

首版产品用语采用“需求、支持、赞助、收餐、反馈、致谢”。不以“活动 / event”作为用户界面的通用对象名称。具体故事可以是集体生日、急救培训或篮球决赛，也可以是机构的定期餐食需求。

本轮定义产品形态与交付，不讨论商业化、抽佣、广告定价或盈利模式。sponsorship 是产品定位，不作为已解决各类实际场景法律性质的结论。原评估中与真实上线有关的规则适用问题保留在依赖清单，不扩大为本轮商业化研究。

成果目标：可用的线上平台、可安装的 CLI + Skill、公开 GitHub 仓库、三类明确标记的示例案例、可承接线下引入的真实案例，以及 X / 小红书传播素材与正式参赛材料。自然 Star 增长是传播结果，不是可以保证的工程输出。

## 2. 已确认的产品决策

| 编号 | 决策 | 产品含义 |
|---|---|---|
| D01 | 网页展示，AI 执行点餐 | 网页提供专属复制 Prompt；用户自己的 AI 客户端通过已连接的麦当劳 MCP 执行操作 |
| D02 | CLI + Skill 可经复制指令安装 | 自动检查或安装 Mc4Need 组件；已有麦当劳连接就复用，缺少连接才引导配置 |
| D03 | 发起方也在 AI 中创建需求 | 确认地址、配送、餐食、份数和时间后生成网页 |
| D04 | 公开发布路径完整可用 | 安装 Skill 的普通用户可以发布；线下邀请是获客渠道，不是权限门槛 |
| D05 | 发起方指定餐食，一人承担整单 | 不拆份认领、不多人拼单；例如 30 份指定套餐由一位赞助人承担 |
| D06 | 承担后立即下单付款 | 不提供先承诺、日后付款的赞助模式；实际创建订单仍需赞助人确认 |
| D07 | 统一致谢，赞助无需逐笔审批 | 发布时接受统一致谢方式；赞助人选择姓名、昵称或匿名，首版不提供自定义广告语、外链和冠名交易 |
| D08 | 公开收货地点与定位 | 需求页显示收货地点名称、地址和地图；电话、私人门牌及配送补充信息另行处理 |
| D09 | 指定餐品缺货暂停赞助 | 发起方更新后再开放；赞助人不能自行替换 |
| D10 | 邮箱验证推荐但不强制 | 首次发布或赞助可使用访客身份；绑定邮箱用于恢复账号和接收邮件通知 |
| D11 | 最晚接单时间 + 付款时限 | 接单成功指麦当劳待支付订单创建成功；付款时限从此时计算 |
| D12 | 定期需求逐期确认 | 下一期生成草稿，发起方重新确认后发布；不自动发布、下单或扣款 |
| D13 | 收餐确认 + 反馈才完成 | 麦当劳订单完成不自动完成平台案例；不强制上传照片 |
| D14 | 取消申请与联系入口并行 | 发起方可申请取消；赞助人操作自己的麦当劳订单；不承诺取消或退款一定成功 |
| D15 | 站内通知 + 可选邮箱通知 | 未绑定邮箱的用户下次访问网页或由 AI 查询时看到消息；不承诺离线即时触达 |
| D16 | 订单留言为基础，联系方式为补充 | 网页与 AI 都可留言；自愿提供的手机号、微信等仅向订单另一方展示 |
| D17 | 状态标明来源与同步时间 | 付款、配送等标明“赞助人客户端同步”；最终收餐与反馈标明由发起方确认 |
| D18 | 演示与真实案例分开 | 演示可以呈现模拟完成，但不能冒充真实履约、触发真实订单或计入真实成果 |

以上决策替代早期文档中的拆分认领、网页独立点餐、强制邮箱验证、仅邀请发布及后台自动周期下单设想。原文保留供追溯，不作为当前实施依据。

## 3. 两个界面的职责

| 界面 | 首版职责 | 用户能完成的事情 |
|---|---|---|
| 公开网页 | 发现与理解 | 浏览需求、查看地点和地图、查看餐食总份数与进度、阅读示例与真实反馈、复制需求专属 Prompt、访问 GitHub |
| 登录后的网页 | 记录与协作 | 查看本人需求/赞助、留言、通知、可选联系资料、收餐反馈和致谢；登录入口由 AI 提供短时一次性链接 |
| AI + Skill | 业务操作 | 安装检查、平台登录、创建和更新需求、读取实时需求、核验餐食、锁定整单、调用本人 MCP 算价和下单、查询状态、取消、留言及反馈 |
| 官方支付入口 | 支付 | 用户在麦当劳官方支持的页面或 App 中自行完成支付；Skill 再查询结果 |
| 管理后台 | 必要运营 | 管理示例、处理举报/异常、暂停违规内容、查看操作记录；不以管理员代录或逐条审批代替公开发布路径 |

网页不要求用户交出麦当劳 Token，也不承诺用户只靠手机网页就能独立点餐。对手机访客应在复制前清楚说明：需要能安装并执行 Skill、能使用麦当劳 MCP 的 AI 客户端。具体支持客户端以实测清单为准，不把普通聊天应用一概视为可执行环境。

## 4. 发起需求的交互

1. 用户从网站复制发布指引，或直接在已安装 Skill 的 AI 中说出需求。
2. Skill 检查 Mc4Need 安装和平台会话。无需邮箱即可继续；绑定邮箱是可选操作。
3. 在发起方本人已连接的麦当劳 MCP 中确定接收地点、可配送门店、指定餐食与总份数、送达安排。机构名称、署名方式及公开定位由用户确认。
4. 区分期望用餐时间与最晚接单时间。只有官方当前可执行的下单/预约范围内才开放赞助，远期内容先保留草稿。
5. 展示发布预览：餐食内容、总份数、公开地点、用餐安排、最晚接单时间、统一致谢方式、单次/重复安排。餐费若展示，应标为带时间的参考价，赞助时重新算价；报价展示形式是实施建议，尚无固定餐价承诺。
6. 用户确认发布，得到需求链接。普通用户无需邀请也能走完整条路径。

页面上的地图坐标不是配送能力证明；发起方账号里的 addressId、门店结果、优惠及报价不能直接当作赞助人账号下可复用的业务凭证。

接收人及公开地点信息须由有权提供的人确认。公开地点与私密配送信息分字段保存，不能把完整订单对象直接序列化到网页。真实机构名称、学校标识及红十字相关标识仅在获得相应确认后使用，不从场景示例推导真实合作关系。

## 5. 赞助的交互

1. 网页显示指定餐食、总份数、地点、时间安排、参考价格（若有）、需求状态和支持入口。
2. 点击“支持这顿饭”获得专属复制 Prompt。它只包含可信安装入口和需求编号/公开链接，不包含用户凭证、私人联系资料或可长期使用的网页登录凭证。
3. AI 检查或安装 Mc4Need CLI + Skill，建立或恢复访客会话；检查已有麦当劳 MCP 连接。安装不等于授权，不自动创建订单。
4. 从平台重新读取需求与版本，确认仍可赞助。赞助人进入整单确认时申请短暂独占锁；锁时长和限频参数尚待技术验证。
5. 在赞助人自己的账号中确定该需求的接收地址、门店、指定餐食、份数和送达时间，重新算出实际总价，包括适用的配送及其他费用。指定餐品缺货就暂停并提示发起方更新，不自动换餐或减量。
6. 展示完整订单与署名选择，赞助人明确确认后调用 MCP 创建订单。不得仅因 Prompt 中写着“支持”就跳过具体金额与订单确认。
7. 成功创建待支付订单后开始付款计时，提供官方支付入口。赞助人付款后由 AI 查询订单，并将最小必要状态回传平台。
8. 网页展示进展与同步时间。可在付款后推荐绑定邮箱，以便恢复记录及获得后续提醒，不用绑定邮箱阻断付款或查看现有订单。
9. 发起方实际收餐并提交反馈后，形成完成案例；署名遵循赞助人选择，反馈中不暴露其私密联系方式。

所有涉及地址、时间、餐食、数量的变更都应使旧确认失效并重新核验，不能在赞助人确认后悄悄替换。这是实现 D05、D06、D09 所需的工程约束，不是新增加的业务角色或审批环节。

## 6. 身份、登录与授权

Mc4Need 身份和麦当劳账号分开。平台访客会话可持有受保护的本地访问凭证，用于管理本人需求和赞助记录；持有者不等于经过实名或机构身份认证。具体凭证、恢复和网页交换协议待技术设计。

- 邮箱自愿验证后绑定，用于账号恢复、跨设备访问和订阅邮件；不是首次操作前置条件。
- 没有绑定邮箱且本地凭证丢失时，不能保证自助恢复；付款后可简短提示保存记录或绑定。
- AI 可生成短时、一次性、用途明确的网页登录链接，网页会话只能访问对应主体的资料；链接过期、重复兑换或撤销应失效。
- 不接受客户端任意提交麦当劳 accountId 就登录他人平台账号；当前没有确认官方提供适合此用途的身份凭证或 OAuth 接入。
- Mc4Need 平台不集中保存用户麦当劳 Token。由用户自己的 AI 客户端使用已有连接；CLI 处理平台 API 与数据整理，Skill 编排已连接的 MCP 工具。若某客户端不能这样协作，应作为兼容性限制报告，不静默转为上传 Token。
- CLI + Skill 借鉴法信 CLI 的安装体验：版本化发布包、依赖准备、完整性校验、客户端适配、自检、升级、恢复与卸载；不复用法信登录方式或任何个人凭证。

## 7. 反馈、取消与通知

收餐确认与反馈是两个逻辑字段，可一次提交。文本反馈或允许公开的链接即可，不以照片为强制证明。默认致谢可以利用平台支持者署名与发起方反馈完成，避免引入每单自定义广告权益。收餐失败、数量不符等反馈进入异常记录，不能生成正向完成案例。

发起方申请取消时，订单立即提供留言区和双方自愿公开给对方的联系方式。平台发出站内通知，已自愿绑定邮件通知的用户另收邮件。申请不直接取消麦当劳订单；由赞助人通过自己的客户端发起取消，再同步实际结果。取消成功与退款到账分别记录。

留言支持异步文本即可，不将实时聊天室、附件传输、已读回执等列为已确认首版要求。通知不能把未绑定邮箱、AI 未运行的用户描述为已被实时触达。

## 8. 初始案例与真实案例

| 场景 | 示范重点 | 公开示例命名建议 |
|---|---|---|
| 希望小学集体生日 | 整单餐食与每期确认 | “乡村小学 · 一起过生日”，标注虚构场景演示 |
| 红十字会急救培训 | 培训批次、接收安排和致谢 | “急救培训 · 为守护者加餐”，不暗示未经确认的官方合作 |
| 大学篮球赛总决赛 | 一次性需求、接单截止与赛后反馈 | “校园篮球 · 决赛后的这一餐”，标注虚构场景演示 |

种子案例以“演示案例 · 模拟完成”展示全链路，分享预览也保留标记。赞助人数、餐食份数、金额、反馈等模拟字段不计入真实成果，不开放真实下单。

真实案例由用户线下获客引入，同时保留公开自助发布路径。Live 仅表示真实需求，不保证已经有人赞助；正式完成依据 D13。至少一个真实完成案例是建议的联合验证目标，取决于真实双方、支付和交付时间，不能用开发者自造记录替代。

## 9. 待验证假设与实施前检查

| 编号 | 假设/未决项 | 需要获得的证据或决策 |
|---|---|---|
| V01 | 访客与 AI 会话可安全绑定，网页登录不被冒用 | 本地凭证、一次性链接、恢复/撤销协议；跨主体访问负例 |
| V02 | 发起方餐食安排能在赞助人账号下复现 | 不复用跨账号地址 ID；真实地址、菜单、配送时段和算价验证；失败转待更新 |
| V03 | AI 安装后能发现平台 CLI 并调用既有 MCP | 支持系统/客户端矩阵、干净环境安装与升级验证；需要重载时清楚提示 |
| V04 | 超时、断连、结果不明可安全对账 | 实际订单创建时间、官方支付有效期、查询和取消能力；不重复下单、不提前释放 |
| V05 | 接单截止与用餐安排匹配 | 当前可预约范围、付款时限、最晚接单配置；具体时限数值尚未选定 |
| V06 | 客户端同步足以支持首版可解释进度 | 来源标签、同步时间、最小化上报、重复/冲突报告处理；不承诺不可伪造的官方验真 |
| V07 | 公开访客发布能应对基础滥用 | 限频、举报、内容隐藏、占位限制与运营处理；参数及证据标准待定，不倒退为邀请门槛 |
| V08 | 所选使用方式符合服务规则 | 核实 MCP 个人用途、第三方凭证、脚本和自动化适用边界；用 Skill 编排不自动证明规则问题已解决 |
| V09 | 状态通知具有可实现的触达范围 | 站内可检索、邮件绑定/退订、发送结果；不声称客户端离线时持续自动同步 |

### 已知外部依据

服务规则的限制与赛事鼓励开发 Skill 的具体边界仍需核实，不能因产品方向确定而视为获得授权。[官方 MCP 服务规则](https://cdn.mcd.cn/cms/pages/MCPServerRules.html)
